# 0001 — db-console 凭据与执行口径:明文存储、执行全放开

- 状态:已接受
- 日期:2025-08-25
- 关联词条:`CONTEXT.md` § db-console(数据库连接)

## 背景

db-console 是 DeepSeek Harness web GUI 的数据库控制台插件,定位为**本机单用户的开发工具**:一个项目一条 PostgreSQL 连接,配置持久化在 Host 侧,跨浏览器刷新/清缓存/切换工作区不失效。

设计过程中对两件事反复拉锯,最终都做了与"直觉安全默认"相反的选择:

### 凭据存储

1. 初始倾向明文 + UI 打码(方案 A);
2. 第一轮改判为主口令加密(方案 B):Host 只存密文,AES-GCM + 口令派生;
3. 加密引出解锁生命周期问题:为满足「强刷浏览器不重登」,口令必须随浏览器持久化(localStorage);
4. 但口令与密文同机同权时,加密只剩"防直接翻 `~/.dsh` 磁盘文件"一层皮——与方案 A 实际安全性等价,却多出整套加解密、解锁流程与密钥管理代码;
5. 终审回到 A:**明文存盘**,以文件权限收紧 + UI 打码作为全部缓解。

### SQL 执行边界

1. 初始选择只读会话(仅 SELECT/EXPLAIN);
2. 讨论强制层级时确认:前端拦截可绕过、语句白名单有解析误伤成本、PG 会话级只读最可靠但用户明确表示「不拦截了」;
3. 终审:**彻底放开**,不做任何语句解析或拦截。

## 决策

1. **连接串明文持久化**在 Host 侧 JSON(DSH storage 惯例位置),原子写入,文件权限收紧(`0600`);UI 一律打码展示(`postgres://user:•••@host:5432/db`)。
2. **无解锁流程**:不存在主口令、不存在解锁态;任何能读到该文件的本地进程都能拿到完整凭据——这是被接受的边界。
3. **执行全放开**:任意 SQL 原样发给 PG;结果区区分「返回 N 行 / 影响 N 行」;不做白名单、不做危险语句确认。

## 备选方案(被放弃的)

| 方案                                               | 放弃原因                                                                                                              |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 主口令加密                                         | 「刷新免重登」诉求迫使口令落 localStorage,加密退化为磁盘卫生,与明文等价但代码复杂度数倍                               |
| Host 内存缓存派生密钥(TTL)                         | 安全性最好,但 dsh 进程重启即要求重输,且仍保留整套加密代码;被便利性否决                                                |
| 只读三层强制(前端提示 + 白名单 + 会话级 read-only) | 用户裁决不要任何拦截;其中会话级 `SET default_transaction_read_only` 是唯一零误伤手段,若未来需要只读语义应从它重新出发 |

## 后果

- **正面**:实现简单、永远免登、写库场景(DML/DDL 调试)不被打扰。
- **风险**(已知且接受):磁盘明文凭据可被本机任意进程读取;控制台可对数据库执行任意写操作乃至 DROP。
- **缓解**:配置文件 `0600`;UI 打码;工具定位为本机单用户。
- **未来出路**:若威胁模型变化,优先级依次是 ① 数据库侧收敛账号权限(真正的安全边界);② PG 会话级只读开关(零解析成本);③ 重新引入加密(须先回答口令放哪才能不自我拆台)。
